The Beginning · Foundation

The Product

A digital library of true conversion-to-Islam stories, in two languages.

True stories

Stories of people who embraced Islam; curated, inspiring content — not auto-generated.

Bilingual

Every story is published in English and Arabic (en/ar) in parallel.

Markdown-based

Each story is a simple .md file with frontmatter — no database.

Serverless

SSG: a static site ready at the edge, no server state to manage by hand.

Narrative note: at its core the product is an archive — not a highly interactive app. This simplicity drives every later decision. Point out that each card reflects a decision we will come back to.
Motivation

The Problem

The original stories are scattered across disconnected platforms, not bilingual, and hard to archive or reach offline.

Fragmentation

No single trusted source for the stories, with consistent quality and a unified narrative.

Language barriers

Arabic and English audiences live in separate information spheres; we need paired texts.

Weak archiving

Sensitive religious content needs durability; do not depend on a dynamic server.

Reading performance

Story readers want instant loading, even on a weak network.

Frame the problem before the solution: we did not start from "we need Next.js" — we started from "we need a bilingual archive". The engineering solution came later, in service of that need.

The Governing Thesis

The Thesis

“Markdown as the database, SSG as the render layer, and no server state.”

Markdown as the database · SSG as the render layer · no server state

The single idea that governs every later decision: the content is the source of truth, and rendering is derived from it.

This is the "mental moment": every technical detail that follows will be measured against this sentence. If a decision conflicts with it, reconsider the decision.
What the Thesis Yields

What Follows from the Thesis

Secure by design

No server means no endpoints to attack and no database to breach. The smallest attack surface.

Fast reading

Simple archiving

Content lives in Markdown, not locked inside a proprietary CMS.

The Decision Journey · 3/4

The Markdown Processing Pipeline

Why Markdown instead of a CMS/database? Because it is a version-controlled, git-able copy of the content. 

// src/lib/story-parser.ts:74-91
export async function parseStoryFile(fileName: string): Promise<StoryData> {
  const slug = extractSlug(fileName);
  const fullPath = path.join(storiesDirectory, fileName);
  const fileContents = fs.readFileSync(fullPath, 'utf8');
  // gray-matter
  const matterResult = matter(fileContents);
  validateFrontmatter(matterResult.data, fileName);
  // remark
  const processedContent = await remark().use(html).process(matterResult.content);
  const rawHtml = processedContent.toString();
  // sanitize
  const contentHtml = sanitizeHtmlServer(rawHtml);
  return normalizeStoryData(matterResult.data, slug, contentHtml);
}

src/lib/story-parser.ts:74-91 :81 gray-matter :86 remark :88 sanitize

Explain the decision in order: gray-matter for frontmatter, remark for the transformation, remark-html for HTML, then DOMPurify for sanitization. Why no CMS? Because the stories are 69 hand-written text files — a CMS would be an unneeded addition (YAGNI).

HYDRATION · 3/5

What Hydration Is

React attaching to the existing tree and adding event handlers — it is not CSR starting from an empty DOM.

useEffect runs after commit; at that point it may read browser APIs and update state in a later render, legitimately.

Any state update after mount — such as reading window or localStorage — must happen inside useEffect, not during the first render.

Core point: hydration ≠ CSR. React does not repaint everything; it attaches handlers onto the existing nodes. The distinction is decisive for understanding mismatch errors.
