خط معالجة Markdown

لماذا Markdown بدلاً من CMS/قاعدة بيانات؟ لأنّه نسخة قابلة للتحكّم والgit من المحتوى.

// src/lib/story-parser.ts:74-91
export async function parseStoryFile(fileName: string): Promise<StoryData> {
  const slug = extractSlug(fileName);
  const fullPath = path.join(storiesDirectory, fileName);
  const fileContents = fs.readFileSync(fullPath, 'utf8');
  // gray-matter
  const matterResult = matter(fileContents);
  validateFrontmatter(matterResult.data, fileName);
  // remark
  const processedContent = await remark().use(html).process(matterResult.content);
  const rawHtml = processedContent.toString();
  // sanitize
  const contentHtml = sanitizeHtmlServer(rawHtml);
  return normalizeStoryData(matterResult.data, slug, contentHtml);
}

HYDRATION · 3/5

ما هي الـhydration

إرفاق React بالشجرة الموجودة وإضافة معالجات الأحداث — ليست CSR تبدأ من DOM فارغ.

useEffect يعمل بعد الالتزام، ويمكنه عندها قراءة واجهات المتصفح وتحديث الحالة في تقديم لاحق صالح.

أي تحديث للحالة بعد الـmount — مثل قراءة window أو localStorage — يجب أن يحدث داخل useEffect لا أثناء أول تقديم.

جوهر: hydration ≠ CSR. React لا يعيد رسم كل شيء؛ يعلّق معالجات على العقد الموجودة. الفرق حاسم لفهم أخطاء mismatch.

بصراحة — مقايضة معلنة

'unsafe-inline' و'unsafe-eval' في script-src (السطر 7) يُضعفان CSP. هذا ضروري حالياً لأدوات التطوير/شرائح معينة، لكنه ثمن معترف به في الخارطة الطريق.

لا تتظاهر بأن CSP مثالي. اذكر الثغرة (unsafe-inline/eval) واربطها بشريحة roadmap — الهدف رفعها عبر nonces مستقبلاً.
